# A：同库事务、兼容迁移与恢复

## 4.23 的权威存储

新增接收原文、状态、去重、冲突、变更游标均放在 **同一个有效业务 ledger.sqlite3**，与订单事务共同提交；不新建一个无法与订单原子提交的旁路 inbox.sqlite3。认证仍在既有 auth/devices 存储，凭据不写进业务原文。主机密钥、可撤销授权与业务数据保持既有分离，恢复文件不携带认证秘密。

设计采用 ledger schema 3。下面是表职责，**不是已生效 DDL**；B 必须在单独迁移文件实现，并同步结构哈希、完整性、恢复和复制校验：

| 表/结构 | 必须保存的内容与约束 |
| --- | --- |
| offline_streams | stream_id、原设备、主体、登记 epoch、创建/停用信息；stream 是受认证登记的设备实例，不允许客户端随意冒用 |
| offline_operations | operation_id 主键、stream/sequence 唯一、目标订单/所有者、租约与身份 epoch、kind、规范原文和摘要、主机收到时间；原件只追加 |
| offline_states | operation_id 外键；received/waiting_dependency/applied/conflict/rejected、版本/原因、最终 request_id/回执引用、下一次可执行时间 |
| offline_dependencies | 当前与前项 ID、同订单/设备/stream 约束、缺失依赖；接收可先保存前项尚未到达的 ID，处理前强校验并检测环 |
| offline_conflicts | 原候选、共同基础、主机当前版本、业务字段差异；所有成本利润字段按读取权限裁剪，原始快照不可变 |
| offline_resolutions | 获授权裁定人、稳定裁定操作 ID、基础版本、选择及生效回执；同候选只允许一个匹配基础的有效裁定，竞争裁定需重新核对 |
| offline_events | 状态变化及来源，仅供受授权维护/业务追溯；与状态事务共存，不生成问题日志目录 |
| order_changes_feed | 单调 change_id、订单/确认版本/归属、需撤销投影的变更；只读投影按权限分页，不能直接把表数据发给子版 |
| 元数据/行映射 | 协议版本、恢复 epoch；现有稳定 line_id 与离线行 ID 的明确映射；不能仅按显示位置合并行 |

接收事务：校验已认证绑定及摘要 → 查原 ID/stream 序号与在线 requests 冲突 → 容量核算 → 追加原件、依赖和初始状态 → COMMIT → 返回 202。未 COMMIT、磁盘满、busy 或连接中断结果不明时不能宣称已接收；按原 ID 核查。相同原件已存在时不重复占容量或插入业务。

应用事务：重新验证当前设备/包/主体权限 → 校验依赖与订单基础版本 → 主机计算/合并 → 同库写订单、历史、requests、审计、feed 和 applied 回执 → COMMIT。抽出可复用的 ledger 事务内变更函数，不嵌套调用当前自开事务的 `store::mutate`。应用 request_id 使用原 operation_id（裁定用独立稳定 ID），写入前核对跨入口指纹；不能一边提交订单、一边另开事务写已处理标志。

认证状态与业务库不做假跨库原子承诺：所有授权变更/撤销与应用检查走同一个短时授权顺序门，门内完成当前身份重验及本地业务提交，明确先完成的事务顺序。网络、等待依赖、重算大报表不占门；统一锁顺序，禁止持业务写锁再反向等待服务锁。发行 session 不承担裁定授权。

重启从 durable states 重扫 received/waiting，不依赖内存队列；没有可永久卡死的 running 标志。崩溃在事务前无效，在事务后同 ID 返回已存结果。等待/冲突按订单隔离，不能用全设备最高序号代替每条结果。队列状态变动也触发主机复制 dirty 标记，即使业务账本金额版本未变。

## 升级与回退

1. 使用既有 owner 排他锁停止本机写入；验证服务、账本 ID、结构哈希、inventory 和数据/认证映射。未知结构、缺库或身份不符停止，**不初始化空库、不覆盖旧文件**。
2. 生成并实际验证可恢复的升级前一致副本与清单。新建 schema 3 表/索引及元数据、更新 user_version/结构哈希在一次本地事务中完成；再次完整性检查。旧订单 ID、金额、owner、历史、证书、服务目录与备份位置均保留。
3. schema 1 先沿受控路径转为 2，再升级 3；升级日记记录源/目标版本及阶段。重启识别已提交或未提交阶段，不能重复生成账本或逐表半迁移。
4. 尚未产生新版本数据时，可停新服务并恢复核验过的升级前副本。已有新单/接收/裁定后不能直接回退旧库；先保全增量、导出并对账，再受控回退。旧程序面对 schema 3 明确拒绝，不能忽略新表继续写。

## 复制与每日恢复门槛

- 新增表全部纳入 schema 3 完整性核对。普通接收改变队列但尚未改变金额，也必须生成可核对的 snapshot 身份，不能被既有金额 revision 去重漏掉。
- 采用新的兼容复制清单版本，区分 schema 3。旧副本不能确认已接收不理解的数据代；保留最后有效代并提示维护端升级，正式端静默。没有自动升主；主机本地确认后的异步复制语义不变，不承诺主机硬盘永久损坏后零损失。
- 新每日逻辑恢复格式 `777-data-backup-v3` 必须包含接收原文、依赖、回执、冲突/裁定及业务 feed 所需状态，Excel 仍从同一一致快照生成。旧 v1/v2 可受控读入，保留原有回执再初始化空离线队列；不能把旧恢复包当成已包含终端未上传数据。
- 还原后新建恢复 epoch、暂停自动应用，重验设备映射、旧回执和未决来源；游标重新绑定。导入不恢复旧会话、密钥或授权。仅在恢复日期之后、旧备份中已不存在的生效回执可能由终端再次送达，必须从原主机增量/终端确认记录核对，无法证明时进入保全，不能直接再次入账。
- 离线租约签名公钥和历史 key_id 可随恢复数据保留供核对；私钥不进业务备份。换机恢复通过维护重绑并签发新租约，保留旧原件而不伪造旧身份。

**启用前必须先完成新格式的写出、读回、故障恢复和新复制端校验；任何一项未就绪都不向终端发布离线能力。** B 可以先交付未启用的接收基础，但不能带未受保护的新队列投入正式使用。

## 终端本机库（D）

每设备独立业务库、确认投影、原始修改/历史和 outbox；本机保存订单与 outbox 必须同一持久事务，成功后才按原业务流程反馈已保存。授权和允许字段在原生层验证，销售缓存不包含全量成本利润。母版的本机未决库放在不会被整代主从复制替换的设备私有位置；子版只保留获授权数据，不能下载统一主数据库。

本机源 ID/计数器、租约、原件和回执都有恢复路径。旧本机副本恢复后，先用原 operation_id 查询/重传原件；新建操作前在线登记新的 stream 并从权威确认区重建，避免回拨序号冲突。不能复制别人的 DPAPI 凭据来换机，不能删除 pending.bin 后另建单；旧 pending 先按原在线 request_id 核清，再转入新流程。

Windows 本机后台负责关闭窗口后的续传与开机恢复；D 需落实设备级生命周期、单实例和正常退出，不能只依赖 React 定时器。卸载保留未确认的唯一数据并提供维护恢复路径，正式端无额外设置/冲突入口。收到 applied 后仍按保留策略保存确认记录，不因收到 202 删除唯一原件。
