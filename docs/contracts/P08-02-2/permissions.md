# 服务端能力和身份边界

## 1. 能力目录

以 `desktop/permissions.json` 为当前目录来源；Host 应从相同版本目录生成/加载规则，不另造一套同名不同义清单。A 不改变现有 UI 文案；backup 的显示名称在 F 改为“业务数据备份”。

| capability | 版本/依赖 | Host 必须控制的行为 |
| --- | --- | --- |
| quote | 两版必选 | 公共报价、计算、新订单；不因此获得历史全量读取或成本字段 |
| orders | 两版 | 客户匹配、订单列表/详情/修改记录，仍执行归属检查 |
| edit_orders | 两版，依赖 orders | 编辑/追加商品及备注；新建和改旧单分开授权 |
| finance | 仅母版 | 成本、利润、内部汇总及财务字段 |
| prices | 仅母版，依赖 finance | 价格预览、发布与成本编辑；普通报价价格读取不要求此项 |
| exports | 两版，依赖 orders | 报价导出任务、历史、下载、重试；只访问允许的任务和归属 |
| settings | 两版；子版只读 | 授权的设置视图；正式端业务目录保存偏好但不应用到 Host |
| backup | 仅母版，依赖 settings | 业务数据备份状态及生成今日备份；不获得任意 Host 路径或恢复管理权限 |

内部财务报表生成/下载需 finance + exports。权限依赖不满足时开发界面补齐选择或说明，Host 始终拒绝非法包，不静默扩大到全权限。未知能力也拒绝，不按未来功能预先放行。

## 2. AuthContext 和鉴权顺序

新上下文至少包含 `principal_kind`（legacy_maintenance / issuer / device / node）、subject、role、site_id、ledger_id、package_id、capabilities、epoch。issuer/node 没有可供业务使用的 subject/role。上下文完全从已验证凭据及 Host 记录构造，不使用请求 JSON 的 role/capabilities。

处理顺序：验证站点/凭据 → 验证主体与关联授权状态/纪元 → 判断路由允许的 principal_kind → 判断 capability 及资源归属 → 执行业务 → 裁剪响应。鉴权必须覆盖 `service.rs` 的提前返回路由、输出下载/重试、转发路径等，不能只包住主 dispatch。

普通母版 device 即使业务 role 为 admin，也不得调用旧账户创建、密码重置、设备票据发行、群集邀请/撤销、发行者管理或恢复管理路由。既有维护身份保持原维护入口，但不编入正式安装包。`Auth::admin` 的粗角色判断不能独自承担新接口鉴权。

节点凭据只允许本节点复制、ack 和经另行验证业务凭据的既有转发；不能把节点秘密换成管理员会话。发行会话只管理本发行者的包，不读取业务。未知路由及无法识别的 pending retry 默认拒绝。

## 3. 数据与旁路

没有 finance 时，从订单/历史/客户匹配/统计/目录/导出/错误详情统一去除成本、利润、毛利及内部财务展示字段。不能只隐藏 React 元素；Host 输出和原生桥接都要裁剪。销售归属过滤应在分页/统计前实施，避免条目数、客户搜索或导出列表泄露他人业务。

财务报表/旧输出文件也要在下载时复核当前权限、产物类型和归属；撤掉 finance 后不能凭旧 URL/任务 ID 下载财务文件。导出重试必须重新检查原任务的真实类型，不能换一个较低权限 API 绕过。前端不接收隐藏备份 UNC、4.23 地址、证书或维护秘密作为业务设置字段。

HTTP 权限外，原生层继续执行编译时功能上限；生效能力是编译上限与 Host 当前授权交集。若包清单/运行二进制宣称不一致，拒绝扩大授权。已授权信息可能已缓存在设备/导出文件中，撤销控制后续访问，不能承诺删除此前合法取得的数据。

备份操作仅调用现有主机每日双格式/双位置流程；用户偏好目录不重定位 Host，客户端不能把请求中的路径当作服务端可写路径。技术错误只进维护日志，业务提交未成功时保留草稿及原请求 ID，禁止伪造已保存状态。
