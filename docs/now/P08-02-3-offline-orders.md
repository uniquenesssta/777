## 1. 目标与既有约束的变更

母版、子版在各自已有业务权限内，断开主服务器后仍可在**当前电脑**创建、查看并继续编辑正式订单；本机事务可靠落盘后才反馈保存成功。订单不因关闭窗口、重启电脑或长时间断网变回草稿。连接恢复后自动上传，4.23 持久接收、去重、处理版本冲突，再向有权限的终端分发统一结果。

此目标替代 P08-02-2 中“断网只能保留草稿、禁止本机正式入账”的后续实现限制。4.23 仍负责统一账本与跨设备汇总，本机正式保存不等于主服务器已收到；不把 4.38 或其他副本自动提升为主服务器，不把多个完整数据库相互覆盖。D 源码在真实登记、有效签名租约及主机显式 apply 后启用本机模式；旧 Host、未启用或未登记终端保持既有在线路径。完整恢复与现场验收仍须 F/G。

当前部署规模按用户最新确认为：一台母版、一个开发者端、一个子版。4.23 统一处理可自动合并的改动；不能自动合并的业务冲突允许获授权母版核对、选择，开发者保留维护能力。子版仅保留选定业务功能，不提供冲突裁定。母版核对结论必须由服务端追加到不可抹去的历史记录；先前“所有冲突仅开发者处理”的范围已被本条覆盖。E 尚未实现，不将任务书修订视为已开放母版权限。

仍保持：正式端无登录/退出登录、无地址或技术错误提示、无问题日志文件、无根目录 `logs/`；后台静默恢复连接。持久订单、同步待上传记录、版本差异与业务回执属于必要业务数据，不是问题日志，也不能为满足“无日志”而取消它们。

## 2. 用户流程与保存语义

| 场景 | 目标行为 |
| --- | --- |
| 已登记终端连接正常 | 保存路径统一使用稳定操作身份；自动提交到 4.23，保留可恢复本机记录，不重复生成订单 |
| 断网或 4.23 暂不可达 | 本机保存正式订单，可继续查询、添加商品和按权限编辑；不给连接失败弹窗，不谎称服务器已收到 |
| 保存后关闭或重启 | 本机订单和待上传操作都保留，重新打开继续编辑；后台恢复后继续上传 |
| 连接恢复 | 后台自动检测，立即唤醒上传队列；失败退避重试，不需要用户点击同步或导入文件 |
| 4.23 已接收但回执丢失 | 用同一操作 ID 查询或重试，不能换 ID 再创建一单 |
| 多台电脑修改同一订单 | 主机校验基础版本，合并无冲突修改；有冲突时保存双方版本，按第 4 节处理 |
| 首次安装从未成功登记 | 不伪造账本或权限。预授权离线初始化不在本轮默认范围；首次在线完成身份与账本确认后启用离线入账 |

“本机保存成功”只能在订单变更与待上传记录同一事务持久化后出现。磁盘满、权限不足或写入失败时保留输入，不能显示成功或悄悄丢单；使用现有业务保存反馈，不暴露内部路径、IP 或技术异常。是否已到达服务器只作为内部状态维护，不增加正式端同步提示条。

## 3. 数据与后台职责

1. **本机业务存储**：持久保存获授权的订单、离线修改、所用价格/业务规则版本及待上传记录。母版复用本机后台职责；子版提供最小持久队列和后台上传能力，不因此携带主机管理权限或完整财务数据。明确子版关闭窗口、开机恢复和卸载时的数据与后台生命周期，不能仅靠页面内定时器保证同步。
2. **身份与幂等**：账本 ID、设备 ID、操作员归属、全局订单 ID、全局操作 ID、基础订单版本、设备内顺序及内容摘要都需持久化。人工订单号与内部唯一 ID 分离，不能依赖本机时间或各机自增号避免碰撞。收到同操作 ID 但不同内容时拒绝冒充重试并保留证据。
3. **主服务器接收**：4.23 后台常驻，校验身份、权限、账本、规则版本与操作依赖；业务变更、去重回执和新版本原子提交。重复请求返回原结果，设备重启或主机重启后仍可核查。
4. **队列与拉取**：保留每笔修改的先后依赖、原始请求和确认状态；批量有限、可断点续传，一笔待处理冲突不能阻塞无关订单。主机已确认内容与本机尚未上传内容分开管理，主机下发或整代副本替换不得覆盖本机未决订单。
5. **权限与撤销**：离线只使用已核定的角色、销售归属及数据范围；本机与主机均做校验。设计离线授权期限和撤销后的处理规则；断网无法实时获知远端撤销，不能承诺即时生效。恢复后主机重验，拒绝/过期/权限变化的内容保留并进入开发者专用处理流程，不能删除或无限重试，也不能默默越权入总账。
6. **业务与财务口径**：本机订单按本机可见范围计算；主服务器报表只统计已接收且有效的统一记录，未解决版本不重复计入。同步确认、冲突裁定及跨机拉取不得重复计算销售额、成本或利润。保留既有按月分页、月内按日和超大报表拆分规则；归属日期不因上传延迟改为上传当天。
7. **输出与备份**：本机已保存但未上传的数据必须有恢复路径；原有主机每日备份只能覆盖主机已接收的数据，不宣称涵盖未上传终端。定义本机恢复文件、未决队列与身份的恢复/换机规则，保留稳定 ID，防止旧备份恢复造成重复入账。沿用主机统一每日 `.qbackup` + 可读 `.xlsx`；报表、报价输出和备份副作用分别幂等，不因重试重复生成。不同终端恢复数据不得带走超出权限的内容。

### 3.1 4.23 的存储位置与网络通道

**`\\192.168.4.23\共享\backup` 只是备份目标，不是业务数据库，也不是上传/合并中转目录。** 不要求在该共享目录内放置三个 Quote777 文件夹，不把 `.xlsx` 或 `.qbackup` 当成正在运行的数据库。

| 位置或组件 | 职责 | 是否需要共享给正式端 |
| --- | --- | --- |
| 4.23 本机 `Quote777Host` | 后台程序、部署与启动资源 | 不需要 |
| 4.23 本机 `Quote777Service` | 统一业务数据库、身份及配置；新增接收回执、待处理操作与冲突记录 | 不需要；仅 Host 管理读写 |
| 4.23 本机 `Quote777Hidden` | 普通本机备份目的地 | 不需要 |
| `\\192.168.4.23\共享\backup` | 固定隐藏备份目的地，接收恢复文件及可读 Excel | 只承接原备份职责，不承接数据库同步 |
| 4.23 的 HTTPS Host 服务 | 接收各终端上传，统一处理并返回结果 | 开放受认证的服务连接，不开放数据库文件 |

新部署沿用三个本机同级目录跟随 Host 的规则；已有部署以有效配置和账本身份为准，不为统一路径搬动或覆盖已有数据。例如 Host 在 `D:\Quote777Host`，同级 Service 可在 `D:\Quote777Service`；这是本机位置示例，不是已核实的现场路径。

现有源码已具备本机数据库与 HTTPS Host：初始化在服务根目录的 `private/ledger.sqlite3` 创建账本，运行时依据节点角色选择有效数据目录（见 `crates/quote-host/src/host.rs`、`service.rs`、`cluster/replica.rs`）。本任务需要给 Host 增加离线操作接收和合并能力，不需要把数据库迁到共享目录。

现场分两种情况处理：已有 4.23 Host 时核对并保留账本、证书和运行配置，再兼容升级；如果实际上只有备份共享而没有 Host，则先在 4.23 本机部署后台与业务存储，不能声称共享目录会自行处理订单。若原数据库丢失而只剩备份，应走已有恢复与身份核对流程，不静默初始化空库冒充原账本。当前未远程核实现场部署，不用历史运行记录推定此刻状态。

### 3.2 4.23 后台处理能力与故障隔离

优先实现“认证接收 → 本机持久化操作 → 去重/按订单顺序处理 → 提交有效版本或保留冲突 → 返回处理回执”。分别记录已接收、已应用、待裁定和被拒绝的内部状态；上传仅被接收不能据此删除唯一的本机原始修改，须按恢复契约保留至可核对的终态。

- 单一权威业务写入由 Host 管理；多个客户端通过协议提交，不共同打开 SQLite 或覆盖整份数据库。
- 有限批次、事务大小及并发，上传限制和积压管理在后台执行；同订单依赖有序，无关订单可继续处理。一笔冲突不能卡住整台服务器。
- 处理回执与去重键持久化；主机重启后续做，不因回执丢失重复入账。大量终端恢复时采用限额和退避，避免同时反复重传全部数据。
- 网络共享写入、Excel 生成和每日备份不得长时间占据订单写入关键区；使用一致快照做输出。共享断线只影响备份交付，不阻塞 Host 本机入账。
- 明确线程/队列/事务职责及资源上限，测量并发接收与重连追赶能力，再根据结果调整。当前没有 4.23 硬件与真实负载证据，不预设并发台数或每秒订单量。
- 主机进程在桌面端退出后继续运行，并按现有 Windows 后台方式开机恢复；机器关机或服务停机期间由各终端保留本机正式单，恢复后续传，不依赖开发者界面常开。

## 4. 重复订单与修改冲突规则

| 情况 | 4.23 处理要求 |
| --- | --- |
| 同一操作重复上传 | 校验内容一致，返回原回执；只入账一次 |
| 相同客户、淘宝 ID 或微信号，不同订单号 | 归集到对应客户名下，保留不同订单；身份匹配本身不是重复订单依据，多个候选不能自动混合 |
| 不同设备新建相同外部订单号 | 作为疑似重复核对来源和内容；保留双方原记录，不凭订单号直接删除、拼单或双计金额；由服务端核定有处理权限的母版或开发者确认保留、归并或更正，子版无此入口 |
| 同一订单分别新增不同商品项 | 使用稳定商品项 ID 与操作 ID；仅在权限和业务规则允许、互不冲突时自动合并并重新校验金额 |
| 同一订单修改互不相关字段 | 按基础版本和字段规则检测；只合并可证明兼容的改动，涉及价格、折扣、金额的关联字段整体校验 |
| 同一字段被改为不同值，或作废与编辑并发 | 保留主机版、本机版和共同基础版本；禁止“最后上传者覆盖”。进入获授权母版或开发者处理入口，选择保留/组合后的业务结果，再生成新版本；子版无冲突提醒或选择入口 |
| 上传被权限、业务规则或账本校验拒绝 | 保存本机原单和原因供获授权开发者处理；不自动改成成功，不转投独立账本，不静默丢弃 |

新增订单、追加商品、编辑、作废及恢复的规则分别定义；不能只覆盖新建订单。未解决冲突保留当前已确认的主机有效版本参与中央汇总，争议增量不重复记账。解决动作也要做版本检查、权限检查和幂等提交，保留基础版本、每个候选值、选定方案、最终值、处理人、时间和理由；更正结论只能新增记录，不覆盖或删除旧裁定。母版复用既有订单详情与修改记录，展示获准的业务冲突及最终选择，不暴露网络、队列等技术信息，不另建问题日志目录。

### Excel 金额修改的显示与保留（用户图片及范围澄清）

用户提供的示例为同一行 `234 → 235 → 255`：**234、235 为红色，最终确定的 255 为黑色**。此红黑表达**仅用于 Excel**；界面继续复用已有“修改记录”的逐版本“修改前/修改后”展示，不新增同款红黑金额排列。现有入口见 `desktop/src/features/OrderHistory.tsx`，订单详情已接入；后续按既有权限接入离线修改及最终生效结果；母版可在获授权的现有业务记录中核对冲突和裁定历史，技术信息仍只在开发者端处理；不新增同款红黑金额界面。Excel 规则如下：

- 每次已保存的金额修改都保留，包括中间多次修改；不能只保留最初值和最终值。按版本及修改关系展示先后，跨设备并发明确各自来源，不能仅凭电脑时间推断最终结果。
- 历史金额使用红色，最终确认生效的金额使用黑色；保持同一订单、同一金额字段的对应关系。最终值再次被修改并确认后，旧最终值转为红色历史，新最终值为黑色。
- 最终确定指完成业务确认/冲突裁定，不是“最后上传”或“最后收到”。冲突未解决时，Excel 保留现有已确认有效值并明确待处理候选，不将某个新上传候选伪装成最终黑色金额；双方版本完整保留。
- 历史项保留修改人、修改时间、来源和版本等业务依据，按权限查看；以“历史/最终”等文字辅助区分，不仅依靠颜色。重复上传同一修改不会新增重复历史项。
- 汇总与财务统计只取当前有效金额，Excel 红色历史金额只供查阅，不相加、不计成新订单；主报表金额列仍只统计有效值。Excel 排列参考用户示例，同一金额字段按历次修改排列，最终确认金额在末尾；超长历史不得截断丢失。

## 5. 母版业务核对与开发者维护边界

- [ ] 正式母版与子版只显示用户封包选定的业务功能；沿用现有保存、订单列表、详情和获准的修改记录。除用户最新明确允许的母版业务冲突核对外，不新增同步、离线状态、重试、维护或技术信息入口，不为正式端重做整套 Figma。
- [ ] 离线保存、后台上传和结果拉取在既有业务入口下工作，不增加登录、连接失败、证书、地址、“部分交付”提示，不生成问题日志。
- [ ] 正式端已有修改记录继续按权限显示修改前后业务值；母版可查看获授权的待核对业务值和历次裁定，子版只读获准的业务结果；不显示设备地址、队列、接收状态或技术拒绝原因。
- [ ] 自动去重、安全合并和规则校验均在 4.23 后台执行；需要人工判断的冲突由后台持久保存，交由获授权母版核对，开发者可维护；不分派给子版。
- [ ] 开发者端优先复用现有查看与修改记录能力；确需新增冲突裁定或维护界面时，才在既有 Figma 文件补充对应授权入口的设计，再接入源码。此设计不作为后台实现的先行阻塞条件。
- [ ] 母版业务裁定和开发者维护分别由服务端单独授权；仅隐藏按钮、改本机版本标记或伪装开发版不能取得权限。正式端缓存、接口返回和本机读回也必须遵守权限，不只隐藏界面。
- [ ] Excel 单独执行红色历史金额、黑色最终金额规则，不把此样式移植到正式端界面。
