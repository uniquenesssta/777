# 报价明细、折扣参与设置与提交恢复（2026-10-20）

基线 `93c9522`，分支 `stage/p08-cutover`。本轮落实用户三项报价要求，并修复后续两张截图中的客户选择/重复核价问题。P08-02-3 E 冲突裁决仍暂停。

## 行为与数据

- 报价录入表隐藏销售单价、K；保留实际计算参数。订单详情原有列不受录入表网格调整影响。
- 商品和折扣均可从左侧拖动；聚焦手柄后上下方向键也可移动。使用指针捕获，不依赖可能被 Windows 原生文件拖放接管的 HTML drag 事件。
- 重排保留行 ID、原订单来源和冻结价格；草稿版本递增并清除旧核价，提交/编辑/离线保存使用同一行序。
- 明细不再显示“顺序折扣”；右侧改为“折扣合计”。价格维护在计价方式下增加“参与折扣”，默认勾选。
- 新字段 `PriceItem.discount_eligible` 是可选布尔值，缺省等于参与；未设置字段的旧价格序列化保持原样，历史哈希不变。发布校验、配置导入、目录返回、订单冻结、公开核价、离线快照及恢复均保留该字段。
- 每条折扣只作用于上方可参与商品的已结算小计，后续折扣继续叠加；未参与商品不进入折扣基数。成本不打折，金额继续使用精确十进制/整数分和既有逐行舍入。
- 例：参与商品 100、免折扣服务 50、90% 折扣、参与商品 100、50% 折扣 → 145；将第一个折扣移到最前 → 150。
- 旧订单继续编辑时采用当时冻结的参与设置；以后改价格维护不会回改旧订单。备份恢复与订单历史完整性检查通过。

## 客户与失败恢复

截图问题的两个原因：原匹配查询仅存于页面局部变量，既只使用最后改动的识别字段，也不能随草稿恢复；在线提交拒绝后原生层无条件清掉计算，但前端仍显示可提交。

- 当前客户/淘宝 ID、微信号、订单号均用于查询；去重合并结果，恢复草稿后也能匹配。分页依据各查询是否还有下一页。
- 已有客户、身份冲突、重复订单号导致保存拒绝时直接打开客户/订单选择弹窗，显示“该客户新建订单”“继续编辑”及明确建立独立客户的选项。不会擅自合并不同客户或订单。
- 900px 自适应选择窗；720px 时订单信息改为两列，操作按钮仍可见，说明不截断。
- 只选择客户不会改变计价输入、来源或核价版本；拒绝后仍有效的原生核价保留，可选择后继续提交。
- 核价确实缺失/过期时前端也立即作废核价，并显示业务恢复弹窗；可以直接重新核价，不需改面积。价格版本过期时重新核价先读取最新价格。核价仍有效的失败提供再次提交；已有订单版本冲突引导读取最新订单。
- 提交结果未知继续走原请求回执/幂等恢复；不另开重复订单。已保存但详情读取失败仍清理原草稿，不提供重复提交。
- 正式端技术错误继续静默、原有权限过滤继续生效；不新增正式端诊断日志。

## 验证

Linux 辅助环境完成，未冒充 Windows WebView2、最终安装包或 4.23/4.38 现场结果：

- Rust 核心 28 项：旧默认、混合参与、连续折扣、调序、精确舍入、配置类型校验、冻结价格。
- Host 客户订单 5 项：真实数据库发布、保存、续编、重排、历史、备份恢复及客户选择原子性。
- 原生离线检查 14 项：新增参与设置保存/重开/调序，原有回执、队列、权限及信任检查。

- Chromium 10 个不同用例通过：新增三项端到端回归，加原有价格编辑、两种角色录入布局、晚到核价、保存后读取失败、客户续编与报表。客户弹窗额外在 1440/720px 验证无横向隐藏操作。
- `cargo fmt --all -- --check`、相关 crate `clippy --all-targets -- -D warnings`、`git diff --check` 通过。
