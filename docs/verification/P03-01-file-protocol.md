## 写入边界

| 写路径 | 锁内操作与冲突条件 | 重复请求与结果 |
| --- | --- | --- |
| 母/子Excel追加 | 读最新已识别工作簿，追加冻结金额/身份/价格信息，稳定ID，重算有效日汇总，保存候选副本、校验、替换并回读 | 同一计算revision复用请求编号；回执存在且内容哈希一致则直接返回已保存，不再追加 |
| 母版追加备注 / 作废 | 读取页面时捕获同一文件字节SHA、订单ID和版本；锁内再校验，拒绝旧页面/版本冲突；不依赖客户、时间和UI行号 | 备注追加而非编辑历史；作废令整单void并增加订单版本，保留所有金额/原行/备注；相同请求重试不重复 |
| 配置保存 | 整份schema有效才进入事务；读取时的SHA用于CAS，其他母版先保存则当前拒写 | JSON保持原业务格式，通过期望内容SHA识别配置效应，副本/日志记录请求；不默默恢复旧价格成交 |
| 提交后视图刷新 | 已验证保存与刷新分别处理；刷新异常仍显示“已保存” | 重新刷新，不因刷新失败另建单 |

工作簿可写范围保守限定当前26列、明确行类型及允许的扩展/附表；未知/坏文件不重建模板。新单身份列完整且UUID/版本/状态一致、每单一条order_total；回执校验请求与文件版本。旧typed记录没有ID时可保留并追加新单，编辑仍只读。无标签历史不猜类型，完整列映射/旧用户/公式缓存与读取失败类型在P03-02处理。

对子版暂时关闭作废和备注写入按钮，直接方法调用同样拒绝。共享文件仍不是认证服务：文件隐藏不提供成本/利润保密；P05才能实施本人数据权限和服务端认证。销售新单视图使用order_id分组，作废行不显示；旧数据分组和读取统计的完整兼容留后续。

## 锁和提交过程

每个文件对应相邻持久锁文件`.文件名.777.lock`。Windows以CRT原生非阻塞字节锁持有打开句柄，辅助POSIX环境用原生flock；锁覆盖读取到替换回读的完整过程，失败/关闭在finally释放。锁内保存host/pid/token/取得时间供诊断；年龄不能作为删除锁文件的依据。进程崩溃后的原生句柄释放需要在目标Windows/SMB验证，本轮辅助环境的杀进程检查不是该实机证据。

先保存同一目录下的唯一临时文件，flush/fsync并回读核对；存在原文件时保存并核对完整字节前像；日志prepared记录目标前后SHA和备份/临时文件名。发布前再核对原件SHA，若检测到外部修改则拒绝替换。替换返回后回读核对内容与请求回执，才报告已保存；替换调用或回读结果不明时保留请求与诊断，不用新请求盲目重试。候选校验失败、备份失败及发布前失败均不删除/替换原件。

本协议只保证遵守同一锁资源的写端。旧版本和外部Excel没有参加锁协议；最终哈希检查能发现已观察的外部变更，但检查后到替换前仍可能被外部编辑器修改。部署验收应退出旧写端、避免外部Excel编辑并发写入；实际共享协议不能满足锁/替换要求时暂停多人写入，不能宣称安全。

`os.replace`只作为同目录发布原语；没有在本轮验证SMB断电持久性、服务器缓存/文件系统保证或Windows共享占用行为。fsync/回读不等于独立备份或跨主机灾难恢复。

依据是Python 3.12官方[msvcrt.locking](https://docs.python.org/3.12/library/msvcrt.html#msvcrt.locking)、[os.replace](https://docs.python.org/3.12/library/os.html#os.replace)、Microsoft CRT[_locking](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/locking?view=msvc-170)。实现并没有引入新第三方锁依赖。

## 未知提交核查

会话内“检查上次写入”使用同一请求编号只读核查。若发现更早prepared日志无法确认，会阻止当前新请求，核查按钮指向阻塞的旧请求；当前请求不能被误报为旧请求已保存。

| 核查状态 | 含义 | 下一步 |
| --- | --- | --- |
| committed | 工作簿中存在有效请求回执，或当前内容与该事务完整后像SHA一致 | 核对原单；同一请求重试只返回原结果，不另建订单 |
| not_committed | 无回执且当前内容仍为该请求完整前像 | 可以使用原请求重试；刷新旧页面，保持原操作/内容，不另造请求去猜结果 |
| not_found | 没有请求回执/日志 | 不能当成未提交，继续保留副本并核查 |
| unknown | 当前内容既不是已知后像也不是前像，或读取/回执校验不能完成 | 暂停该文件新写入，保留诊断材料，人工核对所有写端与日志 |

退出或崩溃后可以用控制台显式只读查询；将路径和编号替换为提示中的原文件和原request_id，不对生产目录递归扫描：

```powershell
py -3 tools/p03_file_check.py --request-status '原文件的完整路径.xlsx' --request-id '提示中的UUID' --output reports/p03-request-status.json
```

配置也使用同一入口，文件扩展名为`.json`时按旁路日志前后像核查。入口只读取指定文件及相邻该请求日志，不写原件、不删除锁、不自动恢复。输出报告路径禁止与被核查原件相同。报告记录当前代码指纹；它不能补证崩溃前另一个版本的行为。

保存后的回执与请求绑定写入目的文件/日期，重试不会因跨天或目录变更自动改到另一个目的地。进程重启后没有自动重建报价草稿或盲目重试；先查询并核对原单。持久恢复工作流仍在P03-04/P05/P08。

## 恢复副本与操作顺序

同目录`.777-recovery`保存每次已存在原文件的`.bak`前像及UUID请求日志，失败的唯一临时文件保留。日志包括协议、请求、操作、内容哈希、原件/后像SHA、备份/候选文件名与结果。原件不存在的首建请求没有前像备份，日志明确backup为null。重复回执不再制造备份；完整内容相同的配置效应直接确认，无需再次替换。

恢复不自动实施：停止相关写端，确认锁持有进程/句柄已结束，不按时间删除锁；保留当前原件、所有候选/备份/日志。逐项核对前像、后像、文件实际SHA与订单/请求回执，先在新副本里验证格式和金额，再决定经明确记录的恢复。候选/备份不要直接覆盖原件，不对结果不明的订单重新收款/提交。尚未开放作废恢复按钮，保留void原行和备注即可供后续稳定身份恢复。

禁止把恢复目录作为隐藏安全边界或完整备份：共享目录同一磁盘丢失时副本也会丢，目录内可能含完整成本/利润。用户要求E盘根Hidden+System主机独立备份、访问控制、计划与保留/恢复演练仍由P05/P08实施。本轮不自动删除旧备份或生产文件。
